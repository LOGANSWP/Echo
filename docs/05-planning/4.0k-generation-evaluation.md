## 3. 首轮筛选（运行前冻结）

首轮使用 `EchoTests/TestData/Generation/4.0k-screen-v1.json` 的 8 条合成用例：简中/英文各 4 条，包含同语言、跨语言、两条来源与来源中嵌入恶意指令。采用固定 greedy、seed 0、完整官方 chat template、context 4096、保留输出 256 tokens。每条先实际 tokenize，满足 `inputTokens + 256 <= 4096` 才调用；不删改样例来掩盖失败，不增设 JSON 修复轮次。

研究 harness 输出每条原文、token 数、时延、JSON/结构结果与来源 ID 判定。语言、事实支持和可读性分别检查，不用 ID 命中率代替。本轮只完成 Agent 初审，人类质量评阅仍为 pending。输出位于忽略的研究目录；这里只登记脱敏的合成数据证据摘要。

**筛选标准（分数不变）**：8 条均有非空合法 envelope、引用仅来自各自输入、正文符合指定语言且无明显无依据事实，才记为该配置通过此开发筛选。任一失败保留结果；禁止把 8 条筛选结果写成 SYN-001 的 ≥99%/≥95% 正式验收。初始计划把该条件同时作为启动转换的前置条件；在四款候选暴露质量与包体独立风险后，修正研究顺序：允许单独进行有界 Core ML 技术探针，回答算子/状态/数值与工件成本问题。探针不改变旧分数、不表示选择生产模型，也不解除质量、工件审批或实机门禁。

**环境**：macOS 26.5、arm64、16 GiB RAM；Python 3.9.6、PyTorch 2.8.0、Transformers 4.57.6、Core ML Tools 9.0。首批 64 次使用 CPU、4 threads。后续只读复核确认沙箱外 `torch.backends.mps.is_available()` 为 true；先前沙箱内 false 不能证明机器无 GPU 后端。后续 MPS/FP16 为独立配置，以控制主机加载与 GPU 转移时的内存压力；同一内容标准与严格无静默回退保持不变，不能与旧 CPU/FP32 数据混成同一速度或数值基线。Mac 推理数据不外推为 iPhone 时延或内存。

冻结的筛选集 SHA-256：`6fc7f653839f06f4d1310dad4203fbcacf554b6edcb4958a943d3ff306f8b316`；harness SHA-256：`0e4b13b826af58de9817c4add03e7330a40f719672d954d17c055b77b997f1d4`。

**第一轮结果：未通过。** 2026-09-07 本地执行 Qwen2.5 `screen-v1` 完成 8/8，但合法非空 envelope 为 **0/8**；没有触及 256-token 上限。`en-single` 增添刷子/教育项目等猜测，多条声称输入不存在；`zh-two-sources` 把“盒内六枚、盒外两枚”误述为六枚被分成两部分；`zh-mixed-language` 输出英文。不能因为原文含正确 UUID 就把它算引用通过。全部 envelope 无效，引用有效率不可计算；未执行语言重试，重试成功率未评估。

CPU 研究运行总时长 81.84s、本地加载 2.88s；这些不代表 iPhone/Core ML 性能。逐条 Agent 审查见 [screen review](4.0k-generation-screen-review.json)，原始输出位于研究目录的 `screen-v1.json`。Agent 内容审查不代表人类审批。保留失败，不装配生产；下一步限定一次显式 `screen-v2` 提示对照（用户消息重申任务与协议，保留 v1），并以原 v1 对比 Qwen3。已经观察过的 8 条只作为开发筛选，不能转称未见正式验收集。

v1 原始脚本按原 hash 保存在忽略目录 `qwen2.5-0.5b/evaluate-screen-v1.py`，Qwen3 v1 使用这份完全相同的脚本。新增 `--prompt-profile screen-v2` 后的工具 hash 为 `3d8fe4e4d7c2771e8dd650e56f18909da444e212261700fe40a7fa2a1e15f464`；默认 v1 仍保持原消息内容，v2 结果另存且不覆盖旧报告。

**Qwen3 v1 对照同样未通过：合法非空 envelope 0/8。** 它更接近要求的内容格式，但有缺少 `sourceMemoryIDs`、把 text 与来源数组拆成不同对象、额外 Markdown fence 的问题；混合来源的中文任务仍保留英文段落。现有生产 JSONDecoder 不接受 fence，本轮没有清理或修复后再计通过。CPU 总时长 62.83s、本地加载 4.75s；同样不是 iPhone 证据。

**Qwen2.5 v2 仍未通过：合法非空 envelope 0/8。** 8 条均带 fence；即使仅为诊断阅读内部对象，也仍有占位 `opaque-memory-uuid`、漏引用字段、`text: "..."`、遗漏重要事实和“空船因此只能向左倾斜”等无依据因果。不能仅删除 fence 就将该配置放行。总时长 138.38s、本地加载 2.26s；受主机负载影响，不据此进行速度排名。

**Qwen3 v2 仍未通过：合法非空 envelope 0/8。** 有 JSON 尾部句号、缺失括号、字段拆错、遗漏来源以及把两条来源合并却只标末条的问题；并非都能归因为 fence。总时长 112.92s、本地加载 4.28s。两款小模型共 32 次输出均未满足本轮原门槛；不对失败结果补字段、拼接对象或猜测引用。

### 3.1 更大模型的有界质量对照

在上述失败后，询问用户质量/包体偏好；暂按已明示的“质量优先”假设研究 **Qwen2.5-1.5B-Instruct**，不把该假设当作商业分发或包体批准。固定 revision 为 `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`；官方元数据权重为 3,087,467,144 bytes，全部 10 文件为 3,098,973,447 bytes。28 层、KV2、head_dim128，4096 下 FP16 KV 为 **112 MiB**。[官方固定配置](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct/blob/989aa7980e4cf806f80c7fef2b1adb7bc71aa306/config.json)

1,543,714,304 参数的理想全 4-bit payload 已为 **771,857,152 bytes**（不含 scales、未量化参数和图），超出新增 ≤400MB proposal；它不是“小模型资源问题已解决”的结论。先用同一冻结测试/工具比较生成质量，是否扩大安装包或选择其他方案需在结果可审阅后明确决定，不能为候选暗改预算。

完整源文件已下载并按官方固定身份独立核验；清单见 [1.5B source manifest](4.0k-qwen25-15b-source-manifest.json)。使用归档 v2 工具、同一 8 例、同一 CPU/FP32/greedy/context/output 配置。下载中的临时文件不算通过证据；恢复下载后仍核对整个权重的预期 SHA-256。

**结果仍未通过**：8 次完成，只有 **2/8** 被现有 parser 接受为非空 envelope，两条都是 `NoSource`；全部结果没有可接受的引用输出。其余有尾部多引号、闭合结构错误、缺引用字段，部分把 schema 中的占位内容当作要总结的信息。一条 parser 接受的输出含重复的空 `sourceMemoryIDs` 字段，已单独记录，不把 parser 接受冒充高质量。总时长 468.07s、加载 15.14s，仅是该次 Mac 研究运行。更大模型在当前 prompt/解码下并未解决闭环，不据此批准其更大包体。

### 3.2 单次受限解码 A/B

为了区分格式能力与事实能力，再冻结一次 **Qwen3-0.6B / screen-v2 / grammar-v1** 对照；案例和 prompt 不变。约束解码仅在下一 token 选择前限制已定义 JSON envelope、UTF-8/字符串转义、字段配对，以及本次实际输入中的 ID 可选集合。正文和引用由模型选择，保留 `[]`/NoSource；禁止自动补绑、合并错误对象、复制全部来源或增加 JSON 修复模型调用。预算耗尽仍未闭合的输出照常失败。

研究使用本机已有 `regex 2026.1.15` 与 Transformers 的 LogitsProcessor 接入点；不是新的 App 依赖或已获批 Swift 运行时。先测试多 token UTF-8、转义、相似 ID、EOS、无合法 token 与原有总超时；另记录 grammar 身份、额外 CPU 时间与停止原因。只要正文失真、遗漏重要信息或语言失败，不能因 grammar 使 schema 通过就批准模型。原 32 次失败保持原样。

**受限解码结果：结构 8/8，整体筛选仍未通过（Agent 逐例审查 4/8）。** 8 条均以 EOS 结束，没有达到输出上限，来源 ID 均在各自 allow-list 中；观察到的正文语言均正确，未发现超出全部输入的新增事实。但 `en-two-sources`、`en-mixed-language`、`zh-two-sources` 合并了两条来源却只引用后一条，属于引用完整性失败；`zh-mixed-language` 只保留第一次测试，遗漏第二次宽底且保持直立的结果。注入案例将命令作为引用文本复述而未执行，不据此推断广泛注入鲁棒性。CPU 总时长 86.49s、加载 2.81s；额外 grammar mask 时间每例 1.26–2.15s，同样不是 iPhone 性能。

固定工具 hash：`4486bd4ee78fbdf14bc4fce6dd13f97f601fdf35c17f477461694d5303c37ead`；grammar 模块 hash：`1d46081a4a346a10b2f2a16297ead5c6cc122b79ded904412f5ea4780a90f927`。原始报告为 `qwen3-0.6b/screen-v2-grammar-v1.json`，逐例审查及报告 hash 登记于 screen review。

### 3.3 来源逐段对照

上述结果将后续问题收敛为来源对应关系，新增一次明确的 **`source-paragraphs-v1 / grammar-v1`** 开发对照。保留同一 8 条原始来源、greedy 和预算；prompt 移除示例 UUID 与冗长 schema，要求按来源顺序分别生成一段、保留关键观察，并由模型返回该段实际来源 ID。仅支持本筛选的最多两条来源；grammar 仍只限定 1–2 段和可选 ID 集合，保留空引用，不替模型指定或补写 ID。

此实验验证来源归属的 leaf 路径，不能等同于跨来源综合、reduce、多层报告或独立正式质量集通过；旧失败保留。结果运行前冻结，不针对逐例失败反复改写来源。

定向样例覆盖中英混合、繁体、组合字符、emoji/ZWJ、罕见汉字、换行/空格、阿拉伯文等。解码结果按官方 NFC 规范化文本比较，不能错误要求分解字符字节原样返回；源记忆本身从未修改。该结果只证明本机 ICU/Unicode 和受限 profile；iOS 18 对照、长输入性能和生产接线仍待交付；本机 Swift grammar/完整 Core ML 生成与内存的后续结果见 §4.4，不能把 180 条 tokenizer 检查算为生成质量样本或生产 E2E。

### 4.3 原生 Swift Core ML 与内存口径

`Scripts/Research/GenerationCoreMLProbe.swift` 已在 **Swift 6 / strict-concurrency=complete / warnings-as-errors** 下编译。模型进程只用系统 Swift/Foundation/Core ML，不加载 Python、Torch 或 Transformers。对同一 context1024 int8 工件运行两次独立 `MLState`、共 45 次顺序预测；8 个固定参考位置的最高分 token 均与官方 FP32 参考一致，每位置仅比较参考最高的 32 个 logit，最大采样绝对误差约 1.41948。这不是全词表浮点保真，也不新增结构化生成或质量样本。首次运行编译/加载约 0.33/4.54 秒；后续为内存口径补测，仍是相同短前缀。

**并发实现发现**：初版将 `MLModel` 持有于 MainActor 并调用异步 prediction，Swift 6 报 sending risks causing data races。探针修正为模型、输入、MLState 的整个生命周期位于一个 `nonisolated` async 函数内，逐步顺序 await；未使用 `@unchecked Sendable`、`nonisolated(unsafe)`、`@preconcurrency` 或降低编译门禁。它只证明单所有者 CLI 可行，未解决生产 Actor 的模型复用、跨请求独占与队列取消；后者仍需实现和测试。

**内存证据**：首次独立进程 `getrusage` 峰值 RSS 为 **1,419,476,992 bytes**。为避免将映射页面误当成全 App 计费内存，第二次增加 Darwin `TASK_VM_INFO`，按字段偏移/返回长度验证可用性，记录加载和每步预测的 RSS、physical footprint 与内核峰值账本；不能以低频采样最大值代替内核峰值。第二次峰值 RSS 为 **1,437,138,944 bytes**，内核 `ledger_phys_footprint_peak` 为 **873,645,304 bytes**，两者口径不同。

这说明“598MB 模型文件”不能代替运行时资源测量；也不能用 Mac 的单模型 footprint 判定 Echo 全 App <1.5GB 门禁通过。该进程没有同时加载 Swift tokenizer、E5/SigLIP2/Whisper 或 UI，没有执行长上下文/完整报告。完整工件 pre/post 校验、源/二进制/参考 hash 和两次原始报告摘要见 [原生 Core ML 审查](4.0k-native-coreml-review.json)。iOS 18 / 实机 / 整体共存内存仍为 pending。

同一 MLState 的预测不能重叠；Actor 的可重入性不提供跨 await 的独占保证。转换成功、编译成功、Mac prediction 成功和 iPhone 成功分别记账。Apple 新 Core AI `.aimodel` 示例要求 iOS/Xcode 27，不能替代这条 iOS 18 路线。[Apple Core AI requirements](https://github.com/apple/coreai-models#requirements-running-and-app-integration)

当前已只读发现可连接的 **iPhone 14 Plus / iOS 18.2.1**，Developer Mode 开启。未安装研究模型或启动设备测试；不把连接状态当测试证据，不记录设备名称、标识符或序列号。它可作为资源受限测试点，不能单独证明所有 iOS 18 支持设备通过。

### 4.4 完整原生 Swift 生成链路

将 tokenizer 拆为共享 `GenerationTokenizer.swift` 后，原 180 项官方对照再次全部通过。新增纯 Swift 字节前缀 grammar 与有界解码器，和原 Python grammar-v1 的 **2,731 个前缀**逐项一致。测试先发现不可能完成的 Unicode surrogate 转义前缀被错误接受，修正为每个十六进制位都验证剩余可补全范围；非法低代理项与不匹配高/低代理项均在解码中拒绝。另有 **12 项实际 Swift 边界检查**覆盖稳定合法 argmax、EOS、added tokens、死路、非有限 logits、上下文预留、顺序位置、输出/预测上限、截止时间与 Task 取消。

`GenerationNativeProbe.swift` 以 **Swift 6 / strict-concurrency=complete / warnings-as-errors** 编译，把 tokenizer、grammar 和 Core ML 放在同一原生进程。每调用独立 MLState，完整 prompt + 256 output tokens 在加载前检查不超过 context1024；预测前后检查取消和单调用 60 秒截止，整轮上限 600 秒。EOS 仅在完整 envelope 后允许，EOS 或第 256 个输出后不再预测。没有正文修复、自动补引用、模型 Stub 或生产 publication。

对 context1024 int8 工件完成原 **8 条冻结样例**：共 **3,574 次 token 预测 / 8 次生成**，全部正常 EOS，输出 84–244 tokens，单例约 **13.45–23.02 秒**，整轮含完整性核验约 **149.32 秒**。8 条输入 IDs 都与官方 tokenizer 对照证据逐项一致，输出 bytes/解码与官方 tokenizer 一致，8 条正文与此前 Python Core ML 同配置输出相同。这只是同机同工件的实测对照，不建立跨硬件逐字一致的契约，也不增加独立质量样本。

JSON/实际 allow-list 结构为 **8/8**，独立的 Mac NaturalLanguage 正文筛查为 **8/8**；仍有桥梁段落重复正文 UUID、将第二条来源的限定语扩写到第一条、中文保留普通英文 `upright`、复述已标注的来源指令等问题。标识符结构合法和主体语言匹配都不能覆盖事实/可读性问题，人工质量批准仍为 false。本原生 CLI 没有接入 LanguageAligner 重试或分层报告；此前一次重试证据仍是独立 host 实验。

同进程加载 tokenizer/grammar/model 后，在末次预测采样点之前记录到的内核历史 **physical-footprint peak 为 974,046,528 bytes**，RSS peak 为 **1,471,954,944 bytes**。这里读取内核历史账本而非只取即时采样最大值；采样发生在 token selection 之前，不声称拿到了进程退出后的完整生命周期峰值。更不代表 iPhone 或 Echo 全 App 共存 <1.5GB 已通过。实际取消实验在第一步 Core ML prediction 返回后注入 Task cancellation，检查立即抛出取消，零生成结果、零 completion；未测量执行中 GPU 抢占或实机取消时延。
